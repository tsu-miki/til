# アウトサイドインで変わるのは設計の順序で、デプロイの順序ではない

呼び出し側のユースケースから API の形を決めても、別々にデプロイする以上、本番に出す順序は提供側が先のまま変わらない。

```http
# 書く順序は利用側が先。出す順序は提供側が先
1. 提供側をデプロイ   POST /users                        # 任意で受ける
2. 利用側をデプロイ   POST /users {"tenant_id": "..."}   # 送り始める
```

書く順序と出す順序が逆になるのがアウトサイドイン特有のねじれで、まだ受け口がないうちにクライアントを出すと落ちる。

利点は、必須にする値の意味を利用側のユースケースから導けること。「未指定のときに何が妥当か」を実装前に言語化できるので、expand で吸収できるかを先に判断できる。パイプラインを跨いで先に渡せるのはデプロイではなく契約で、その仕組みが consumer-driven contract にあたる。

参照: https://martinfowler.com/articles/consumerDrivenContracts.html
