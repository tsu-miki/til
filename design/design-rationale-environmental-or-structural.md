# 昔の制約でできた設計をやめてよいかは、理由が環境由来か構造由来かで決まる

設計の理由には、当時のハードやプロトコルのように前提が変われば消える環境由来のものと、データの依存関係のように前提が変わっても残る構造由来のものが混ざっているので、環境が変わったときは理由を分けて、構造由来が残っているかだけを見る。

```
// 「ブラウザから N+1 を投げず BFF に寄せる」の理由を分ける
環境由来: HTTP/1.1 の同時接続 6 本の上限
          → HTTP/2 の多重化で消えた
構造由来: 一覧のレスポンスを見るまで次の N 件が決まらない
          → 多重化しても往復の段数は減らず、それがユーザーの回線に乗る

// 構造由来が残っているので、寄せる判断は残る
```

理由が環境由来だけなら、前提が変わった時点でやめられる。危ないのは環境由来の理由のほうが有名なときで、それが消えたことをもって設計ごとやめてしまい、生きている構造由来の理由まで失う。「昔からこうしている」と言われたら、当時の制約を特定して終わりにせず、構造側の理由が別にないかを探す。

参照: https://datatracker.ietf.org/doc/html/rfc9113
